# Data Model: Change Request Workflow

## Overview

The model uses Better Auth for user accounts and sessions, plus two application tables for roles,
change requests, and review decisions. All timestamps are UTC. Application tables refer to the
Better Auth user identifier; no application table stores passwords or session secrets.

## Entities

### User (Better Auth)

Represents an authenticated person.

| Field | Meaning | Rules |
|---|---|---|
| `id` | Stable user identifier | Primary key; generated by the auth library |
| `name` | Display name | Required by account registration |
| `email` | Login email | Required and unique under the auth library's normalized identity rules |
| `emailVerified` | Whether the email was verified | Managed by the auth library; feature routes require an authenticated account |
| `createdAt`, `updatedAt` | Account timestamps | UTC |

Better Auth also owns its Account, Session, and Verification records. Those records are managed by
its schema and migration tooling rather than duplicated in ChangeFlow tables.

### UserRole

Represents one server-assigned permission membership. Separate rows allow one person to be both a
Requester and Reviewer.

| Field | Meaning | Rules |
|---|---|---|
| `userId` | Better Auth user identifier | Foreign key to User; part of composite primary key |
| `role` | `Requester` or `Reviewer` | Non-null; part of composite primary key; never accepted from public signup input |
| `createdAt` | When the membership was assigned | UTC |

**Assignment rules**: New accounts receive `Requester` through server-side provisioning. Reviewer
membership is granted only by trusted seed/admin setup. Removing a membership affects the next
protected operation because authorization reads current membership from storage.

### ChangeRequest

Represents a proposed change and its current workflow state.

| Field | Meaning | Rules |
|---|---|---|
| `id` | Request identifier | UUID primary key |
| `title` | Short description | Required; trimmed; must not be blank |
| `description` | Proposed change | Required; trimmed; must not be blank |
| `reason` | Why the change is requested | Required; trimmed; must not be blank |
| `requesterId` | User who created it | Required foreign key to User; immutable after creation |
| `status` | Current workflow state | One of `Draft`, `PendingReview`, `Approved`, `ChangesRequested` |
| `version` | Current concurrency token | Required opaque UUID; replaced after every successful mutation |
| `createdAt` | Creation time | UTC; immutable |
| `updatedAt` | Most recent mutation time | UTC |

Indexes: `(requesterId, createdAt)` for requester lists and `(status, createdAt)` for pending review.
No uniqueness constraint is placed on title or description because duplicate requests are allowed.

### ReviewDecision

An append-only record of one review outcome. Multiple rows for a request preserve prior review rounds
after a requester revises and resubmits it.

| Field | Meaning | Rules |
|---|---|---|
| `id` | Decision identifier | UUID primary key |
| `requestId` | Reviewed ChangeRequest | Required foreign key |
| `reviewerId` | User who made the decision | Required foreign key to User |
| `decision` | `Approved` or `ChangesRequested` | Required |
| `reason` | Feedback when changes are requested | Nullable; optional by clarified product decision; approval reason is not collected |
| `decidedAt` | Decision time | UTC |

Index: `(requestId, decidedAt)`. A decision and the corresponding ChangeRequest state/version
update MUST be committed in the same transaction.

## Relationships

- User `1 -> many` UserRole.
- User `1 -> many` ChangeRequest as requester.
- User `1 -> many` ReviewDecision as reviewer.
- ChangeRequest `1 -> many` ReviewDecision.

## State and Mutation Rules

| Current state | Action | Next state | Actor and conditions |
|---|---|---|---|
| No request | Create | `Draft` | Authenticated Requester; valid required text |
| `Draft` | Edit | `Draft` | Requester owns request; expected version matches |
| `Draft` | Submit | `PendingReview` | Requester owns request; complete fields; expected version matches |
| `PendingReview` | Approve | `Approved` | Reviewer role; reviewer is not requester; expected version matches |
| `PendingReview` | Request changes | `ChangesRequested` | Reviewer role; reviewer is not requester; optional reason; expected version matches |
| `ChangesRequested` | Edit | `ChangesRequested` | Requester owns request; expected version matches |
| `ChangesRequested` | Resubmit | `PendingReview` | Requester owns request; complete fields; expected version matches |
| `Approved` | Any mutation | Rejected | Approved request is immutable |

Every mutation checks the current state and version within the write operation. Review transitions
also check the current user's role and requester identity before writing. If the conditional update
affects no row, the application distinguishes an unavailable resource, an invalid current state,
and a stale version without overwriting data.

## Visibility Rules

- A Requester can list and read only their own requests, including requests in any state.
- A Reviewer can list and read requests only while they are `PendingReview`.
- A person holding both roles sees the union of those two sets. Holding both roles never permits
  review of their own request.
- A request outside the caller's visible set is returned as not found to avoid disclosing its
  existence.

## Validation and Integrity

- `title`, `description`, and `reason` are trimmed and rejected if empty or whitespace-only.
- A Reviewer cannot make a decision on their own request, independent of role membership.
- `Approved` is terminal and immutable.
- All writes require the exact current version token; stale requests cannot use last-write-wins.
- ReviewDecision insertion and the matching state transition are atomic.
- Requester identity and creation time cannot be changed by update operations.
